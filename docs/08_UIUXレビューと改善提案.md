# 総合体育館 施設管理：UI/UXレビューと改善提案

作成日：2026年9月10日  
対象：`disaster_prevention_demo02`  
範囲：現在の実装に対するレビューと改善提案。**本書作成に伴う画面・コードの修正は行っていない。**

## 1. 結論

次の改善では、**「対象を探す → 記録を読む → 判定を記録する → 必要なら訂正する → 元の作業へ戻る」までを安定して完了できること**を優先したい。

現在は日本語文言の整理に加え、施設カルテ、設備ごとの履歴、関連記録へのリンク、スマートフォン向けの画面切り替えが実装されている。単に画面を眺める段階から、記録をたどれる段階に進んでいる。

一方、判定後に訂正できない、再読込で判定が初期化される、履歴では判定結果より確認者だけが変わる、といった点が残る。また、スマートフォンでは情報を減らす工夫があるものの、利用判定の理由やデモ日時の説明まで隠れる。

優先するのは次の3点。

1. **判断と記録の信頼性**：判定結果・確認者・日時・保存範囲を一致させ、訂正できるようにする。
2. **一覧と施設カルテの使いやすさ**：対象を探し、同じ操作で詳細を開き、元の文脈へ戻れるようにする。
3. **端末ごとの情報設計**：小さい画面でも判断理由・デモの前提・操作対象を失わないようにする。

## 2. 調査方法と評価の範囲

全8画面の表示コンポーネント、共通シェル、CSS、`data/suirei.ts`、施設カルテ要件を確認した。今回のレビューは**ソースコードに基づく評価**であり、ブラウザでの実操作やスクリーンショット評価ではない。

下記では、コードから確認できる事実と、そこから予想される利用上の影響を分けている。表示崩れ、押しやすさ、読了時間、実際のフォーカス移動、端末固有の挙動は未測定。実画面での確認計画を第9章に記載した。

以前の文言監査をそのまま再掲してはいない。現在削除されている説明や、追加済みの機能を「未実装」とは評価しない。また、本書は防災・建築・設備の判断基準を検証する資料ではなく、それらの記録と判断を扱うUI/UXの提案である。

## 3. 現在の実装で維持したい点

| 実装済みの内容 | 評価 |
|---|---|
| 「場所・設備一覧」「要対応事項」などの日本語名称 | 何を見る画面かが以前より分かりやすい。旧称へ戻さない |
| 場所・設備の利用判定と、体育館全体の開館判断の区別 | 個別の「利用可能」を建物全体の承認と混同しにくくしている |
| 場所・設備・設備履歴を関連付ける施設カルテ | 記録をたどるための基本構造ができている |
| `zone`・`equip`・`from`付きの記録リンク | 選んだ対象と移動元を引き継ぐ土台がある |
| 画像確認からカルテへ移動できるリンク | 記録の根拠を確認する導線が追加されている |
| 記録なしの場所を残し、不明な項目を正常で埋めない | 記録が不足していることを隠さない |
| スマートフォン向け下部ナビ、縦積み、詳細シート | モバイル対応はすでに存在する。今後は情報の欠落や操作干渉を改善する段階 |
| 関連付け図の折りたたみ | 主な確認・対応事項に画面を使う方向は妥当 |
| 色と文字を併用した判定表示 | 色だけで状態を理解する必要がない |

## 4. 課題と改善提案

優先度は、**P0：誤解・訂正不能・操作阻害につながるもの、P1：日常業務の効率、P2：仕上げ・将来拡張**とする。P0は現実の事故発生を認定する意味ではなく、改修の順序を表す。

## 5. 推奨する画面構成

### 施設の状況

上から「体育館全体の状態」「確認が必要な項目」「場所・設備の4判定」「配置図・資料連携」の順を基本にする。写真と81%の表示は、状況を判断するための主情報より強くしない。

```text
体育館全体：条件の確認が必要          デモの基準日時
開館前に確認すること：車両／備品／発電機／消火器

利用可能 10件        条件の確認が必要 4件
利用不可 2件         利用可否が未確認 2件

関連する場所・設備を見る → 配置図／一覧
資料取り込み 5 / 8項目 → 未完了の内容を見る
```

数値や条件の定義は現行データに合わせる。画像判定を入力しただけで開館可能へ変更しない。

### 場所・設備一覧とカルテ

上部に名称検索と状態フィルター、本文に対象一覧を置く。カルテでは「現在の記録上の判定 → 根拠 → 履歴 → 次の確認操作」の順にする。施設の竣工・面積等は折りたたみ可能な基本情報にまとめ、毎日の作業の開始位置を占有しすぎない。

全行から同じ形式でカルテを開き、その中から要対応事項・画像確認・帳票へ移動できる構造を推奨する。重要案件の直行リンクを併設すれば、現在の短いデモ導線も保てる。

### 画像確認

「判定待ち／確認済み」を分け、確認対象・参照する記録・判定操作を同じまとまりに配置する。判定後は結果と訂正操作を残す。画像から判断できない場合には「資料確認が必要」として作業を中断できるようにする。

### 帳票

二つの帳票を比較できる現在の構成は維持する。対象の欄を選ぶと参照元と対応先が固定で強調され、解除できるようにする。モバイルでは帳票をタブで切り替える案と、現在の縦積みを実機で比較する。

### モバイル共通

主な画面に直接移動できる下部ナビは維持する。「確認」は「画像確認」など、幅が許す範囲で対象を補う。詳細をモーダルにするなら、開いている間は下部ナビを操作対象から外し、閉じた後に元の場所へ戻す。

## 6. 優先する3つの操作シナリオ

### A. 期限超過の設備を確認する

施設の状況 → 期限超過の一覧 → 発電機のカルテ → 点検資料と保管日・期限を確認 → 元の一覧へ戻る。

完了条件：資料保管日を点検実施日と誤解せず、元の対象・表示モードを保持して復帰できる。

### B. 画像を判定し、訂正する

画像確認 → 元記録を見る → 画像確認へ戻る → 判定を入力 → カルテで結果を確認 → 誤りがあれば訂正。

完了条件：判定結果・確認者・日時が同じ内容で表示され、訂正が関連画面に反映される。施設の利用可否を自動で承認しない。

### C. 記録が不足している対象を調べる

未確認2件 → 屋上・空調設備 → 不足する記録を確認 → 確認待ちとして残す。

完了条件：「未確認」を「利用可能」や「記録なしだから問題なし」と誤解しない。不足情報と次の手段が分かる。

## 7. 実施順序と概算

既存実装を使うフロントエンド中心の概算。工数は実画面確認後に見直す。バックエンド、実資料の作成、認証、外部API、業務ルールの確定は含まない。

| 段階 | 対象 | 目安 | 成果 |
|---|---|---|---|
| 事前確認 | PC・モバイルで現状を再現し、判断用語・保存範囲を確定 | 1〜2人日 | 再現手順と確定仕様 |
| 第1段階 | 判定訂正・保存表示・カルテへの結果表示、履歴の日付と種別 | 3〜5人日 | 記録の一貫性を確保 |
| 第2段階 | 一覧・詳細の操作統一、フォーカス、復帰、検索 | 3〜5人日 | 対象を探して戻れる導線 |
| 第3段階 | モバイルの理由表示・デモ表示・ナビ干渉、帳票とAIの調整 | 2〜4人日 | 小さい画面でも意味と操作を維持 |
| 最終確認 | 主要シナリオ、実機・キーボード、修正確認 | 1〜2人日 | 受入結果 |

合計の目安は10〜18人日。新しい本番保存基盤や点検票のデータ入力を含める場合は別見積もりとする。

## 8. 今回の次段階に含めないもの

- 配色やブランドの全面刷新。現在の明るい業務画面を基礎に改善する。
- AI APIへの接続。まず定型回答で操作と期待を一致させる。
- 開館可否の自動承認。画像確認・設備の記録・開館の決定を分ける。
- 市版との実データ連携、全庁の修繕優先順位、予算計画。
- 根拠のない修繕履歴・点検結果の追加。空欄を見栄えのために埋めない。

| 復帰 | AI・画像確認・帳票→カルテ→戻る | 元の会話・対象・位置を維持する |
| データ例外 | 不正なzone/equip、記録なし、画像失敗 | 無言の空表示を避け、戻る手段と状態説明がある |
| 帳票の比較 | マウス、タッチ、キーボード | 選択した対応箇所を維持でき、解除方法が分かる |
| 履歴の意味 | 点検、保管、期限、撮影、棚卸 | 日付と種別が実際の記録内容に一致する |

利用者確認では、施設管理担当に近い人に第6章の3シナリオを説明なしで操作してもらう。所要時間だけでなく、「どの記録を根拠にしたか」「未確認をどう理解したか」「自分が何を記録したと思ったか」を確認する。少人数の確認結果を、利用者全体の達成率として一般化しない。
